# 04 三组性能对比与结论

数据来源：`03_吞吐实验.md`，统一统计 step 2–11。

## 1. 主要结论

在本次 8×A800、Qwen3-4B、DAPO GRPO、colocate 短窗口实验中：

- 单 LoRA 与全参的 step time 相差 0.06%，系统吞吐接近。
- 当前 dense Mixture-LoRA 比单 LoRA 慢 28.56%。
- Mixture 增加的 62.57 秒中，41.82 秒来自 rollout，占 66.8%。
- 三组平均 response 长度相差不到 0.3%，工作量处于同一水平。
- Actor 阶段系统显存均值中，单 LoRA 和 Mixture-LoRA 比全参分别低 30.3% 和 23.8%。
- 端到端峰值由 rollout 主导，Mixture 比单 LoRA 高 1,838 MiB。

这些数字衡量当前实现，包括 token router、四个 expert 的 dense 计算、Top-K 组合、
SGLang external model 和相关分布式处理。它们不代表 Mixture-of-LoRA 算法无法优化的
固定成本。

## 2. 相对变化

| 指标 | 全参 → 单 LoRA | 单 LoRA → Mixture |
|---|---:|---:|
| step time | +0.06% | +28.56% |
| rollout time | +1.85% | +36.75% |
| actor train time | -2.15% | +16.89% |
| response 吞吐 | -0.32% | -22.17% |
| actor train 吞吐 | +1.92% | -14.41% |
| actor 阶段系统显存均值 | -30.29% | +9.34% |
| actor 阶段系统显存 P95 | -35.12% | +6.94% |
| actor 阶段系统显存峰值 | -34.26% | +7.74% |
| 窗口内系统峰值显存 | +24 MiB | +1,838 MiB |

全参与单 LoRA 的各项差异位于 ±2.2% 内。由于实验只有一次十步窗口，结论限定为
“两者表现接近”，不进一步断言差异来自统计噪声。

Mixture 的耗时增加与吞吐下降方向一致，幅度明显超过全参与单 LoRA 的差异。

## 3. Step time 分解

定义：

```text
other_time = step_time - rollout_time - actor_train_time
```

| 组 | rollout | actor train | other | step 合计 |
|---|---:|---:|---:|---:|
| 单 LoRA | 113.79s | 76.92s | 28.40s | 219.11s |
| Mixture | 155.61s | 89.91s | 36.16s | 281.68s |
| 增量 | +41.82s | +12.99s | +7.76s | +62.57s |

增量占比：

- Rollout：66.8%。
- Actor train：20.8%。
- 其他阶段：12.4%。

`update_weights_time` 在单 LoRA 和 Mixture 中分别为 4.34 秒和 4.25 秒。现有数据
不支持将 other time 的 7.76 秒增量归因于权重同步。

## 4. Rollout 开销解释

单 LoRA 的 adapter 对所有 token 固定，可以在 rollout 前合并进 base。Mixture 的
Top-K expert 由 token 输入决定，无法提前形成一个统一的静态权重增量。

当前 SGLang external model 会执行 router，并计算四个 expert 的 LoRA 输出，随后使用
Top-K 权重组合结果。训练端使用相同的 dense executor 语义。该设计优先保证训练端、
rollout 端、checkpoint 和权重同步的一致性，但没有跳过未选中的 expert 计算。

因此本次 36.75% 的 rollout time 增量包含两部分：

1. Token router、Top-K、权重组合和 external model 的结构性开销。
2. 当前 all-expert dense executor 带来的可优化计算。

Grouped sparse 或融合 kernel 可以减少第二部分，并保留当前路由公式、参数布局和
checkpoint schema。

## 5. Actor 训练开销

Mixture 相对单 LoRA 的 actor train time 增加 16.89%，actor train tokens/s 下降
14.41%。Mixture 的每个 routed site 包含四组 expert 参数和一个 router，当前执行器
在 forward/backward 中计算全部 expert，因此训练端同样存在可优化的冗余计算。

Base 参数已经冻结，不产生 base 梯度或 optimizer state。冻结参数降低了可训练参数量，
但端到端 GRPO 的主要耗时仍包含 base model forward/backward、rollout 生成和通信，
因此参数量下降不会自动转换成同等比例的 step time 加速。

## 6. 显存解释

### 6.1 Actor 训练阶段

| 组 | 均值 | P95 | 峰值 |
|---|---:|---:|---:|
| 全参 | 38,259 MiB | 46,391 MiB | 47,550 MiB |
| 单 LoRA | 26,669 MiB | 30,100 MiB | 31,258 MiB |
| Mixture-LoRA | 29,158 MiB | 32,190 MiB | 33,678 MiB |

单 LoRA 冻结 base，不为 base 保存梯度和 optimizer state，因此 actor 阶段均值比全参
低 11,590 MiB。Mixture 只训练 expert 和 router，均值仍比全参低 9,101 MiB；四组
expert、router 及 dense 计算使它比单 LoRA 高 2,490 MiB。

Actor 阶段区间由 TensorBoard 的 actor 耗时和权重同步耗时重建，随后过滤 5 秒 NVML
样本。图中的均值、P95 和峰值都统计该阶段同一卡上的全部 colocate 进程，因此适合比较
部署条件一致时的系统差异，不等同于框架 allocator 的组件级显存分析。

### 6.2 端到端容量峰值

| 组 | step 2–11 窗口峰值 | 整个作业峰值 |
|---|---:|---:|
| 全参 | 61,632 MiB | 62,268 MiB |
| 单 LoRA | 61,656 MiB | 61,656 MiB |
| Mixture | 63,494 MiB | 64,084 MiB |

三组统一设置 `sglang-mem-fraction-static=0.7`。SGLang rollout 会预留相近大小的静态
显存池，生成阶段的 KV cache 和 batch 又会把显存推到该容量附近，因此端到端 NVML
单卡峰值接近。该指标主要反映 rollout 配额，适合判断验收 workload 能否运行，无法
反映 LoRA 在 actor 阶段的全部显存收益。组件级归因仍需要使用 profiler 按 allocator
category 记录内存。

## 7. Mixture 的价值与当前代价

Mixture-of-LoRA 的目标是提高冻结 base 条件下的 adapter 容量，并让不同 token 使用
不同 expert 组合。它主要服务于模型容量和样本效率，不承诺当前 dense 实现一定比全参
训练拥有更高端到端吞吐。

是否值得承担当前 28.56% 的短窗口开销，需要结合 Mixture 相对单 LoRA 的 reward、
收敛速度和样本效率判断。本轮实验完成系统验收和性能测量，没有设计同 token budget
下的最终训练质量对照。

## 8. 结论边界

- 只测试 Qwen3-4B、8×A800、colocate、rank 16、4 experts、Top-K 2。
- 三组使用相同硬件和软件规格，但来自不同实验批次。
- 统计窗口为 10 step，不能代替长程平均和重复实验置信区间。
- 没有覆盖不同 expert 数量、Top-K、sequence length 和并行配置。
- 没有比较三组在相同 wall-clock 或训练 token 下的最终 reward。

## 9. 后续性能工作

1. 使用 profiler 分解 router、Top-K、expert A/B、权重组合和 external model 开销。
2. 在现有 `RoutedLoRAExecutor` 接口下实现 grouped sparse 或融合执行器。
3. 只计算 Top-K 选中的 expert，并覆盖空 expert、token 分组和反向恢复顺序。
4. 在训练端和 SGLang 端对比 dense/sparse 的数值、梯度、吞吐和峰值显存。
5. 使用多次稳定窗口报告均值和方差，再评估是否切换默认执行器。
